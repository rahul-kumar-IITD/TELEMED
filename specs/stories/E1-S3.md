# E1-S3: Patient can register and log in

- Epic: E1 (Platform and Identity)
- Layer: API
- Group: B
- Estimate: M
- Depends on: E1-S1, E1-S2
- Brief criteria covered: AC-01

## Description

Patients self-register with email, password and profile details (full_name, age, gender, phone as contact details) and log in to receive a short-lived JWT. Role is never accepted from the request body. Passwords are hashed with argon2 and login failures reveal nothing about which part was wrong.

## Acceptance Criteria

1. POST /api/auth/register with a valid email, an 8+ character password and a valid profile (full_name, age, gender, phone) returns 201 with a non-null user_id and role PATIENT.
2. A role field supplied in the registration body is ignored and the created user always has role PATIENT.
3. Registering an email that already exists, compared case-insensitively, returns 409.
4. Passwords of 7 characters or 129 characters return 422, while passwords of exactly 8 and exactly 128 characters are accepted.
5. The stored password_hash starts with '$argon2' and never equals the plaintext password.
6. POST /api/auth/login with correct credentials returns 200 and a JWT access token with an expiry; a wrong password, an unknown email and a deactivated account all return 401 with the identical generic body.
7. Registration also requires a profile of full_name, age, gender and phone; the initial profile is stored as version 1 in patient_profile_versions, and a registration missing any of the four, or with an age that is not an integer in 1..130, or an unsupported gender value (FEMALE, MALE, OTHER, UNDISCLOSED are valid), returns 422 with field-level errors.
