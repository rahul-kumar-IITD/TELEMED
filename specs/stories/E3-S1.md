# E3-S1: Stub integrations sit behind injectable interfaces

- Epic: E3 (Appointment Booking and Lifecycle)
- Layer: Service
- Group: B
- Estimate: M
- Depends on: E1-S2
- Brief criteria covered: AC-06

## Description

Video, payment/refund, e-prescription and notification integrations are defined as Service-layer interfaces with stub implementations. Stubs never touch the appointment event log; each call emits a single structured log line with identifiers only. Tests inject spies.

## Acceptance Criteria

1. VideoService, PaymentService (charge and refund), PrescriptionService and NotificationService interfaces exist and the default application wiring binds a stub for each.
2. Each stub call emits exactly one JSON log line containing only identifiers such as appointment_id and event type.
3. Stub calls leave the appointment_events row count unchanged.
4. The video stub returns a deterministic placeholder join URL containing the appointment id.
5. A test can override any stub with a spy through dependency injection and read its recorded calls.
